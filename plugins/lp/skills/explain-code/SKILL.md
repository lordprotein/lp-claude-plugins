# Explain Code

## Overview

Помогает быстро понять код: что изменилось и зачем, или как устроена существующая часть системы. Результат — короткое читаемое объяснение со схемой.

Это **не ревью**: никаких оценок качества, поиска багов и предложений по улучшению. Только понимание.

**Три режима** (определяются по аргументу автоматически):

- **Изменения** — рабочее дерево, коммит, диапазон, MR/PR, задача Jira.
- **Код** — файл, папка, функция, класс, компонент.
- **Flow** — как работает часть системы, описанная словами.

Скилл только читает: ничего не редактирует, не коммитит и не пушит (единственное исключение — локальный ref при fetch MR/PR).

## Workflow

### 0) Разбор аргумента

1. Если в аргументе есть `--html` — запомнить и вырезать (см. раздел 4).
2. Если есть `--diff` — запомнить и вырезать (модификатор для пути).
3. Определить режим по остатку, **первое совпадение побеждает**:

| Аргумент | Режим | Как получить материал |
|---|---|---|
| пусто | изменения | `git diff HEAD` + untracked (`git status --porcelain`). Если пусто — коммиты текущей ветки относительно базовой: `git diff $(git merge-base origin/<base> HEAD)..HEAD` |
| ссылка на Jira (`…/browse/<KEY>` или `…selectedIssue=<KEY>`) | изменения | Взять `<KEY>` из URL → задачу через Atlassian MCP (`getJiraIssue`), если доступен → коммиты `git log --all --grep=<KEY>` → объединённые изменения этих коммитов. Если коммитов нет — сказать об этом и объяснить только суть задачи |
| ссылка на MR/PR | изменения | GitLab `…/-/merge_requests/<id>` → `git fetch origin merge-requests/<id>/head:mr-<id>`. GitHub `…/pull/<id>` → `git fetch origin pull/<id>/head:pr-<id>`. Diff от `git merge-base origin/<base> <ref>` до `<ref>` |
| `<a>..<b>` | изменения | `git diff <a>..<b>` + `git log <a>..<b>` |
| sha (`git rev-parse --verify <arg>^{commit}` успешен) | изменения | `git show <sha>` |
| фраза про изменения: «последний коммит», «последние N коммитов», «что изменилось в ветке», «мои правки» | изменения | Перевести в git-эквивалент: `HEAD`, `HEAD~N..HEAD`, коммиты ветки, рабочее дерево — дальше как в строках выше |
| существующий путь (файл/папка), опционально `path:line` | код (или изменения с `--diff`) | Читать файлы, их зависимости и потребителей; в больших файлах только нужные диапазоны строк. С `--diff` — режим изменений, ограниченный путём (`-- <path>`) |
| идентификатор (функция, класс, компонент) | код | Найти определение через `rg`, дальше как для пути |
| свободный текст | flow | Найти точки входа по ключевым словам (роуты, обработчики, экшены, компоненты, команды) и трассировать вызовы |
| неоднозначно | — | Показать 2–3 кандидата через AskUserQuestion |

**Базовая ветка:** `git symbolic-ref --short refs/remotes/origin/HEAD`, иначе `main`, иначе `master`.

### 1) Контекст проекта

Перед анализом прочитать `CLAUDE.md` в корне репозитория. Если его нет, взять из `README` только раздел про архитектуру и структуру. Цель: понять слои и терминологию, объяснять в терминах проекта.

### 2) Сбор материала

**Режим изменений**

1. `git diff --stat`, затем полный diff без шума: lockfiles, сгенерированный код, снапшоты, дампы i18n/локалей исключить pathspec, например `-- . ':!*.lock' ':!*-lock.*' ':!*.snap' ':!*generated*' ':!*locales*'` (адаптировать под проект; те же исключения для `git show <sha>` и diff MR/PR). Исключённые и тривиальные файлы описывать по `--stat`, их diff читать, только если он важен для вопроса. Больше ~800 строк: сначала сгруппировать файлы по модулям/фичам, читать по группам.
2. `git log --format='%h %s%n%b'` по диапазону: сообщения коммитов как источник «почему».
3. Удалённое и переименованное: `rg` по репозиторию только для публичных и нетривиальных символов (экспорты, API, общие утилиты), понять, чем заменено или почему больше не нужно. Локальное достаточно понять по самому diff.
4. Новые и изменённые публичные экспорты: найти потребителей (`rg`), чтобы построить поток «было → стало».

**Режим кода / flow**

1. От точки входа пройти по вызовам вглубь до границы (сеть/API, хранилище, UI, внешняя библиотека). Глубина — 3–4 уровня, дальше только назвать.
2. «Почему так»: `git blame -L a,b <file>` ключевых мест (или `git log -L a,b:<file> -s --format='%h %s'`) → `git show -s <sha>` для сообщений коммитов. Патч (`git show <sha> -- <file>`) смотреть только у коммитов, важных для объяснения.

**Контекст задачи (все режимы)**

Задача берётся только из ссылки-аргумента: самостоятельно не искать (ни по ключам в коммитах, ни по ветке). Если без неё «зачем» остаётся неясным, попросить ссылку на задачу или её текст. Пользователь отказался: продолжить без неё, помечая догадки.

### 3) Вывод (терминал)

**Режим изменений:**

```markdown
## Суть
1–3 предложения: что теперь работает иначе и зачем.

## Было → стало
ASCII-схема потока (до 15 строк). Узлы: [+] новый, [-] удалён, [~] изменён.

## Что изменилось
Группы по смыслу, не по файлам:
- **[+] Название** — что и зачем, `path:line`
- **[~] Название** — что поменялось и зачем, `path:line`
- **[-] Название** — почему удалено и чем заменено

## Почему такой подход
2–4 пункта, у каждого источник: (Jira) / (коммит abc123) / (код). Догадки — «(предположение)».

## Связи
Кто кого вызывает, что затронуто косвенно.

## Обратить внимание
0–3 неочевидных эффекта. Нет — раздел не выводить.
```

**Режим кода / flow:**

```markdown
## Суть
1–3 предложения: что это и за что отвечает.

## Схема
ASCII-схема: вход → шаги → результат (до 20 строк).

## Шаги
1. Шаг — 1–2 строки, `path:line`
2. ...

## Ключевые части
- `name` — роль

## Почему так
Из blame, коммитов, задачи (если предоставлена). Догадки — «(предположение)».

## Подводные камни
0–3 неочевидных места. Нет — раздел не выводить.
```

**Правила:**

- Язык ответа — язык пользователя.
- Не пересказывать код или diff построчно — объяснять смысл.
- Тривиальное (импорты, форматирование, переводы, переименования без смысла) — одной строкой.
- Ссылки только в формате `path:line`.
- Не выдумывать причины: всё, что не подтверждено Jira, коммитом или кодом, помечать «(предположение)».
- ASCII-схема — простые прямоугольники и стрелки, без лишнего декора.

### 4) Флаг `--html`

Сбор материала и разделы те же, меняется только доставка:

1. Загрузить скиллы `artifact-design` и `artifact-diagramming`.
2. Схема — inline SVG; узлы [+]/[-]/[~] выделены цветом. Группы изменений / шаги — сворачиваемые (`<details>`), в каждой не больше одного фрагмента кода или diff до ~10 строк.
3. Записать файл в scratchpad-директорию: `explain-<key|sha|mr-id|slug>.html`. Опубликовать через Artifact tool с `icon: "code"` и `description` = суть.
4. В терминал — только «Суть» и ссылка на страницу.

## Edge cases

- **Нет git-репозитория** — доступны только режимы кода и flow.
- **Пустой diff** — сказать об этом и предложить: коммит, диапазон или режим кода.
- **MR/PR fetch не удался** (нет доступа, другой remote) — сообщить и попросить ветку или sha.
- **Atlassian MCP недоступен при ссылке на Jira** — попросить текст задачи.
- **Слишком широкий flow** (найдено много точек входа) — показать кандидатов и уточнить.
