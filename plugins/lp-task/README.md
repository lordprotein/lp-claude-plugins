# lp-task

Плагин Claude Code для полного цикла работы над задачей в одном или нескольких репозиториях: прочитать задачу из трекера → выбрать проекты → для бага воспроизвести его в браузере → спланировать → создать ветки и реализовать → проверить в браузере → закоммитить → запушить и создать MR/PR → отправить команде сообщение со ссылками.

Диалог с пользователем ведётся на русском.

## Команды

| Команда | Что делает |
|---|---|
| `/lp-task:do <ссылка \| ключ \| status> [--without-loop]` | Читает задачу, спрашивает, в каких проектах нужны изменения, для бага решает, нужно ли воспроизводить его в браузере (простые баги, причина которых видна в коде, без прогона), и предлагает прогон, когда причина зависит от данных, планирует от наблюдаемых данных, после одобрения плана создаёт ветки от удалённой основной ветки (main/master, без вопроса) и реализует без вопроса в автономном цикле `lp-task-loop` (с `--without-loop` или просьбой «без loop» как обычно): при одном фиксе на несколько проектов сначала первый проект и его проверка |
| `/lp-task:test-browser [reproduce \| verify] [ключ] [--screenshots yes\|no]` | Работа с задачей в Chrome через Chrome MCP в одном из двух режимов. «Обнаружение» (`reproduce`): воспроизвести баг до фикса и записать в состояние задачи, что видно, какие данные это вызывают и какая ветка кода. «Проверка» (`verify`): критерии приёмки и регресс вокруг изменений, сценарий воспроизведения идёт первой строкой. Проекты проверяются одновременно, каждый в своей вкладке (по очереди только mobile после desktop, проекты на одном порту и Playwright). Про скриншоты не спрашивает: по умолчанию только нужные проверке, скриншот каждой строки с `--screenshots yes` или по просьбе в запросе |
| `/lp-task:commit [описание фикса] [--with-comments]` | Коммитит изменения задачи во всех её проектах (первый коммит или новый fix-коммит) с сообщением по шаблону, без вопроса о нём; с `--with-comments` (или `git.commitDescription: true`) добавляет в коммит описание: что сделано и почему так, затем предлагает запушить |
| `/lp-task:push [ключ]` | Пушит ветки, создаёт MR (GitLab) или PR (GitHub), затем одновременно собирает сообщение для команды (`mr-message`) и, если `isAllowHowToTestAfterPush: true`, сообщение для тестеров (`how-to-test`) |
| `/lp-task:mr-message [ключ] [группа] [ссылки MR]` | Собирает сообщение для команды со ссылками на MR/PR задачи (ключ задачи в нём ссылкой на задачу, если она известна) и сохраняет его для копирования (кнопка «MR» мода `lp-copy-bar`). Работает и для веток, запушенных вручную: ищет MR по ветке (GitLab MCP или `glab`, GitHub MCP или `gh`), ссылки можно передать аргументами, найденное записывает в состояние задачи. `/lp-task:push` вызывает его сам. Срабатывает и на просьбы вроде «сделай сообщение для MR» |
| `/lp-task:sync-base [ключ]` | Rebase веток задачи на свежую основную ветку во всех проектах, помощь с конфликтами, затем по подтверждению push с `--force-with-lease` для уже запушенных веток |
| `/lp-task:how-to-test [ключ]` | Собирает короткое сообщение для тестеров: затронутые участки приложения с серьёзностью 🟢/🟡/🔴 и страницей, таблица «До / После», доработки сверх задачи, кейсы «Проверить» (у каждого «Где», «Шаги», «ОР», «Варианты»). Кейсы берутся из воспроизведения, `test-browser` и критериев `lp-task-loop`, плюс таблица «Проверил разработчик» (Где, Что проверял, Результат) из последнего `test-browser`, если он запускался. Ещё: что потенциально может сломаться, изменения API, данные и условия, «Не баг», автотесты. Статусы, enum и поля пишутся как в коде. Карта влияния кешируется в state, повторный запуск без новых коммитов не читает дифф заново. Сохраняет его как rich text для комментария Jira или чата, по умолчанию без копирования (копирует кнопка мода `lp-copy-bar`). Срабатывает и на просьбы вроде «напиши для тестеров, как проверить» |
| `/lp-task:init [путь]` | Создаёт конфиг в диалоге |

Команды лежат в `skills/<имя>/SKILL.md`. `commit` и `push` модель запускает только по вашей явной просьбе («закоммить», «запушь», команда) или ответу «Да» на «Запушить изменения?», сама по себе никогда. Push на ветке задачи без этого блокирует хук.

Агент `browser-tester` (`agents/`) выполняет прогон чек-листа в браузере (Claude in Chrome, запасной вариант Playwright MCP) для `/lp-task:test-browser` и возвращает компактную таблицу; в режиме `reproduce` он вместо чек-листа воспроизводит баг и возвращает наблюдаемые данные и путь в коде, без моков. Чек-лист строится по `references/browser-testing.md`, правила прогона зашиты в самом агенте: позитивные, негативные и граничные сценарии, состояния, приоритеты P1-P3, таблица «тип изменения → какие кейсы добавить», безопасные способы негативных проверок и строка покрытия в отчёте. То, что не удалось проверить на реальных данных (нет данных на стенде, недоступен сервис, редкое состояние), команда мокает сама, без вопроса, самым маленьким подходящим способом: подменой ответа запроса в странице, подменой данных в странице, а если иначе нельзя, временной правкой кода, которая удаляется после проверки и никогда не коммитится. В отчёте такие строки помечены `✅ мок: <что подменили>`, под таблицей указано, почему без мока нельзя. Строки, которым мок не помогает (нужен логин, запрещённое действие), остаются ⚠️ с причиной.

## Связанные плагины

- `lp-task-loop`: `/lp-task:do` реализует план в автономном цикле (реализация, проверка, ревью, скептик, доработка). Без этого плагина или с `--without-loop` реализация идёт как обычно.
- `lp-code-test`: `/lp-task:do` чинит или удаляет сломанные изменениями юнит-тесты только через `/lp-code-test:unit`. Без этого плагина тесты не трогаются, а в итоге перечисляются.
- `lp-code-review`: `/lp-code-review:review` читает тот же конфиг (`stateDir`, `review.*`) и умеет брать MR из состояния задачи (`mr`).

## Установка

```
/plugin marketplace add lordprotein/lp-claude-plugins
/plugin install lp-task@lp-tools
```

## Конфиг

Все значения, специфичные для проекта, хранятся в конфиге, а не в плагине:

1. первый `.claude/lp-task.json`, найденный от текущей папки вверх — его можно положить в репозиторий или в папку с несколькими репозиториями, тогда он подхватится в каждом из них;
2. иначе `~/.claude/lp-task.json`;
3. найденный конфиг накладывается поверх [`config.default.json`](config.default.json).

Создайте его через `/lp-task:init` или вручную по образцу [`config.example.json`](config.example.json). В конфиге обычно есть внутренние ссылки и названия — не храните его в публичных репозиториях (`.gitignore` / `.git/info/exclude`).

| Поле | По умолчанию | Назначение |
|---|---|---|
| `tracker.type` | `jira` | `jira` — через Atlassian MCP, при недоступности — в браузере; `url` — всегда читать страницу задачи в браузере |
| `tracker.issueUrl` | — | Шаблон ссылки на задачу с `{key}` |
| `tracker.keyRegex` | `([A-Z][A-Z0-9]+)-(\d+)` | Всё совпадение → `{key}`, последняя группа → `{num}` |
| `tracker.titleStripPrefixes` | `[]` | Префиксы, которые убираются из названия задачи для `{title}` |
| `git.host` | `gitlab` | `gitlab` (MR через push options) или `github` (PR через GitHub MCP, запасной вариант `gh`) |
| `git.branch` | `{key}` | Шаблон ветки, `{key}` / `{num}` |
| `git.commit` / `git.mrTitle` | `{key}: {title}` | Сообщение первого коммита / заголовок MR |
| `git.fixCommit` | `{key}: fix ({summary})` | Сообщение fix-коммита |
| `git.commitDescription` | `false` | Добавлять в каждый коммит описание: что сделано и почему так. Разово: `/lp-task:commit --with-comments` |
| `git.mrDescription[]` | `["{issueUrl}", "", "{title}", "", "{commits}"]` | Описание PR для GitHub, по строке на элемент: `{issueUrl}`, `{title}`, `{key}`, `{commits}` (список коммитов задачи) |
| `git.ignorePaths` | `[]` | Локальные пути, которые не считаются изменениями и не коммитятся |
| `mrMessage.header` | `""` | Значение `{header}`, например упоминание команды |
| `mrMessage.lines[]` | `["{header}", "{mrTitle}", "", "{links}"]` | Шаблон сообщения для команды, по строке на элемент: `{header}`, `{key}`, `{num}`, `{title}`, `{mrTitle}`, `{issueUrl}`, `{links}` |
| `mrMessage.link` | `* {label}: {url}` | Шаблон строки со ссылкой в `{links}`: `{label}`, `{id}`, `{url}`, `{base}` |
| `mrMessage.clipboard` | `false` | Сразу копировать сообщение после push как rich text (macOS). По умолчанию только сохраняется: копирует кнопка мода `lp-copy-bar` |
| `howToTest.header` | `""` | Первая строка сообщения для тестеров, например упоминание |
| `howToTest.maxCases` | `6` | Сколько тест-кейсов максимум в сообщении для тестеров (🔴 и 🟡 не обрезаются) |
| `howToTest.environment` | `""` | Строка «Стенд» в сообщении для тестеров, например где доступна сборка |
| `howToTest.clipboard` | `false` | Сразу копировать сообщение для тестеров (macOS). По умолчанию только сохраняется: копирует кнопка мода `lp-copy-bar` |
| `isAllowHowToTestAfterPush` | `false` | Собирать сообщение для тестеров (`how-to-test`) в конце `/lp-task:push`. Нет ключа или `false`: после push не собирается, только вручную `/lp-task:how-to-test` |
| `stateDir` | `~/.claude/lp-task/state` | Файлы состояния задач; там же `<key>/messages/` с сообщениями для повторного копирования |
| `review.postToMr` | `ask` | Для `/lp-code-review:review`. `ask` — предлагать публикацию замечаний в MR; `never` — не предлагать |
| `review.minSeverity` | `medium` | Для `/lp-code-review:review`. Минимальная серьёзность для публикации: `critical`, `high`, `medium`, `low` |
| `review.gitlab.mcpServer` | `gitlab` | Для `/lp-code-review:review`. Имя GitLab MCP сервера; запасной вариант `glab` |
| `projects[]` | текущий репозиторий | `id`, `label`, `path`, `pm`, `lint`, `dev`, `mobile`, `autoDetectOnly`, `notes[]` |
| `planNotes[]` | `[]` | Дополнительные правила для шага планирования |
| `pushNotes[]` | `[]` | Правила для push и MR-сообщения: деление MR на группы и когда группу можно пушить (см. «Несколько MR») |
| `browserTest.forbiddenActions[]` | платежи, ввод учётных данных, необратимые действия с аккаунтом | Что никогда не делается при проверке в браузере |
| `browserTest.mobileViewport` | `390x844` | Размер экрана для проектов с `mobile` |

Строка шаблона, в которой все плейсхолдеры оказались пустыми, выбрасывается, а пустая строка `""` остаётся разделителем. `{links}` раскрывается в строки по `link` для каждого проекта с MR. Если `link` начинается с `* ` или `- `, в рабочий чат ссылки вставятся маркированным списком. Пример:

```json
"mrMessage": {
  "header": "@acme-team",
  "lines": ["{header} {mrTitle}", "{issueUrl}", "", "{links}"],
  "link": "- {label} → {url}"
}
```

`autoDetectOnly: true` помечает проект (обычно общую библиотеку), который не предлагается при выборе проектов, но добавляется автоматически, если исследование показало, что задача его затрагивает.

### Несколько MR

`pushNotes` описывают обычным текстом, как проект выпускает MR. Например, общая библиотека живёт в отдельном репозитории, а приложения берут её опубликованную версию: тогда сначала нужен MR только в библиотеку, а MR в приложения идёт после того, как новая версия опубликована и прописана в них.

```json
"pushNotes": [
  "If the task changes ui-kit, split the MRs into two groups: `kit` (only ui-kit) and `apps` (the other task projects); otherwise one group",
  "Push `kit` first. Push `apps` only when the published @acme/ui-kit version with the task changes is set in the package.json of every app of the task; until then the apps wait"
]
```

`/lp-task:push` пушит только группы, для которых условие выполнено, остальные помечает «ждёт». Когда версия опубликована и поднята коммитом (`/lp-task:commit`), повторный `/lp-task:push` пушит следующую группу. На каждую группу сохраняется своё сообщение `mr-<группа>`, и мод `lp-copy-bar` показывает для него отдельную кнопку («MR kit», «MR apps»). Если задача разделилась на группы уже после того, как часть MR создана (общая библиотека вошла в задачу позже), `/lp-task:push` всё равно сохраняет `mr-<группа>` для каждой группы, у которой такого сообщения ещё нет. Без `pushNotes` всё как раньше: одно сообщение `mr`.

## Правила безопасности

- Никакого push без явной команды; без amend; force push — только `--force-with-lease` и с подтверждением.
- Не трогает чужие изменения (никаких `stash pop` / `reset --hard` / `restore` для изменений, сделанных не им).
- Ветки создаются только от `origin/<base>` (основная ветка репозитория) после `fetch`.
- Никакого упоминания ИИ в коммитах и MR.
- При проверке в браузере не выполняет запрещённые действия и не вводит учётные данные.

## Хуки и утилиты

Часть правил продублирована хуками плагина (`hooks/hooks.json`, нужны `bash` и `jq`):

- коммит с `Co-Authored-By`, «Generated with» или `noreply@anthropic.com` в команде отклоняется (в любом репозитории);
- `git push` на ветке задачи отклоняется, если нет свежего (до 15 минут) маркера `<stateDir>/<key>.push-allowed`. Маркер создают только `/lp-task:push` (в том числе после «Да» в `/lp-task:commit`) и `/lp-task:sync-base`. В репозиториях без задачи lp-task push работает как обычно;
- `git stash pop` / `apply` в репозитории задачи отклоняется, если stash не `lp-task <key>`;
- запись в `<stateDir>/…/messages/` из shell (`echo >`, heredoc, `python`, `node` и т.п.) отклоняется: файлы сообщений пишутся только инструментом Write, иначе мод `lp-copy-bar` не покажет кнопку копирования. Чтение файлов и вызов `copy-rich.js` разрешены;
- после `/compact` хук `SessionStart` возвращает в контекст активную задачу: ключ, ветки, проекты, статус коммитов и MR, путь к одобренному плану (поле `plan` в состоянии).

Сообщения для копирования (MR для команды, сообщение для тестеров) сохраняются в `<stateDir>/<key>/messages/`, по умолчанию без копирования в буфер. Мод `lp-copy-bar` показывает над полем ввода кнопки, чтобы скопировать их.

`bin/lp-stop-port <порт> [--force]` освобождает порт dev-сервера (TERM, `KILL` только с `--force`, порты ниже 1024 запрещены). Плагин кладёт его в PATH инструмента Bash; `/lp-task:test-browser` вызывает его, когда порт занят сервером другой ветки. Чтобы не было запроса разрешения, добавьте в `permissions.allow` правило `Bash(lp-stop-port *)`.
