# CLAUDE.md

Marketplace `lp-tools` for Claude Code and Codex. No build, test or lint — only markdown, JSON and YAML executed by Claude Code or Codex. `AGENTS.md` is a symlink to this file.

## Claude Code and Codex

Both clients are supported. The Claude format is the source of truth, the Codex files are generated and never edited by hand.
- Generated by `scripts/sync-codex`: `plugins/<plugin>/.codex-plugin/plugin.json`, `.agents/plugins/marketplace.json`, `plugins/<plugin>/codex-agents/*.toml` (from `agents/*.md`). `scripts/sync-codex --check` fails when they are out of date, `.githooks/pre-push` runs it.
- After changing a plugin: bump `version` in `.claude-plugin/plugin.json`, run `scripts/sync-codex`, commit the generated files with the change.
- Plugins without `skills/` (mods such as `lp-copy-bar`) are Claude-only and skipped by the script.
- Tool names in skills are read by the model, so a few Claude names are allowed when they map to a client tool: `AskUserQuestion` (native choice tool; without one, a plain message with numbered options), the `Skill` tool (call the skill by name), `ToolSearch` (load deferred tools, a no-op where tools are not deferred). Do not add new ones without a neutral fallback sentence.
- Otherwise skills and references stay client-neutral: no `${CLAUDE_SKILL_DIR}` (say «next to this SKILL.md»), no other Claude tool names (`mcp__claude-in-chrome__*` only in agent `tools:` frontmatter); say «the browser MCP available in the session». Paths go through `${CLAUDE_PLUGIN_ROOT}`; Codex sets it for hooks (next to `PLUGIN_ROOT`), whether it is substituted in skill bodies is not verified.
- Hooks: Codex runs them only for plugins installed manually in the desktop app, after a trust review. The hook format is compatible (checked in the Codex docs): matcher `Bash`, `tool_input.command` and `cwd` on stdin, deny via `hookSpecificOutput.permissionDecision`, `SessionStart` matcher `compact`, `CLAUDE_PLUGIN_ROOT`. Do not use PreToolUse outputs Codex does not support (`ask`, `continue: false`, `stopReason`, `suppressOutput`): they mark the hook as failed. Codex calls hooks «a guardrail, not a complete enforcement boundary».
- Agents: edit `agents/*.md` only, the Codex TOML is generated from them. The generator maps `effort:` (xhigh to high) or `model: haiku` (to low) to `model_reasoning_effort`, never copies model names, and adds a read-only line to roles without Edit/Write in `tools:` (Codex cannot restrict tools or the sandbox per agent). Whether Codex loads plugin-bundled agents is not verified; the Codex loop skill falls back to a general subagent.
- A skill that differs too much between the clients gets a hand-written Codex version in `plugins/<plugin>/codex-skills/<name>/SKILL.md`; `sync-codex` then points the Codex manifest to `./codex-skills/` instead of `./skills/` (so such a plugin lists in Codex only the skills of `codex-skills/`: copy the others there too). The Claude files stay untouched by Codex concerns.
- `lp-task-loop` has two skills `run`: Claude `skills/run/` (Workflow `loop.js`, `${CLAUDE_SKILL_DIR}` allowed) and Codex `codex-skills/run/` (the model orchestrates subagents itself: no resume, no git-write hook, `--max` and the budget held by the text). The Codex token budget is measured by `plugins/lp-task-loop/bin/lp-loop-tokens`, which sums the growth of `output_tokens` in the Codex session logs (`~/.codex/sessions`) of the sessions whose cwd is the repo (`start` remembers the repo's logs and a marker file, `spent` reads only those and the logs newer than the marker); if the logs cannot be read the budget is switched off with a note in the report. When the loop logic changes, change both skills. Text that must be equal in both is wrapped in `<!-- sync:ID -->` ... `<!-- /sync:ID -->` (now `snapshots` and `criteria`): edit it in the Claude file, `scripts/sync-codex` copies it into the Codex file and `--check` fails on a difference. The agent prompts are shared (`agents/*.md`, Codex TOML generated).
- Check both: `claude plugin validate .` and install the marketplace in Codex.

## No project specifics

These plugins are used across unrelated projects, and none of them may know anything about a particular one.
- No project names, repository or folder names, paths, domains, hosts, ticket keys, team names, people, package scopes, branch or script names (e.g. a project's own `dev:*` command), stack choices or rules that come from one project.
- Everything project-specific lives in the project: its `CLAUDE.md`, its `.claude/lp-task.json` (`notes`, `planNotes`) or user settings, never in a plugin.
- Examples, configs, evals and docs use neutral placeholders (`acme`, `example.com`, `ACME-123`) and generic data.
- Before committing, search the diff for names from the projects you work on.

## Structure

- `.claude-plugin/marketplace.json` — marketplace manifest, lists every plugin in `plugins/`
- `plugins/<plugin>/skills/<name>/` — skills, invoked as `/<plugin>:<name>`
- `plugins/lp-task/` — task flow, invoked as `/lp-task:<name>`: `skills/` (do, commit, push, mr-message, sync-base, test-browser, how-to-test, init), `shared.md` (config, hard rules, state, «Which task»), `references/`, `agents/` (`browser-tester`), `hooks/` (git guards, context after compaction), `bin/lp-stop-port`
- `plugins/lp-task-loop/` — skill `run` (setup, then the workflow `skills/run/loop.js`: implement/verify/skeptic/review loop), `agents/` (`implementer`, `verifier`, `skeptic`, `reviewer`), `hooks/` (no git writes during the loop)
- `plugins/lp-code-review/` — skill `review`
- `plugins/lp-code-test/` — skills `unit`, `e2e`
- `plugins/lp-explain-code/` — skill `explain`
- `plugins/lp-copy-bar/` — mod (TypeScript hooks module `hooks/register.tsx`, state contract `types/index.d.ts`, tests `hooks/*.test.tsx`): copy buttons above the prompt for the messages lp-task saved in `<stateDir>/<key>/messages/`. Check with `claude plugin validate` and `claude plugin test`

## Editing guidelines

- Skill names in `SKILL.md` are short and have no plugin prefix — the plugin namespace adds it (`unit` → `/lp-code-test:unit`)
- New skill → new folder in `plugins/<plugin>/skills/`, add it to the tables in the root `README.md` and the plugin `README.md`, and to the description in its `plugin.json`
- New plugin → new folder in `plugins/` with `.claude-plugin/plugin.json`, `README.md`, an entry in `marketplace.json` and in the root `README.md`
- A plugin cannot read files of another plugin (`${CLAUDE_PLUGIN_ROOT}` is its own folder): call the other plugin's skill via the Skill tool and inline the config defaults it needs
- Every commit that changes a plugin bumps `version` in its `plugin.json` (semver: patch for fixes and wording, minor for new commands, skills or behavior, major for renames and removals). Without a bump installed copies do not update
- Skill-specific rules live in the skill's own `CLAUDE.md`
- Commands are skills (`skills/<name>/SKILL.md`); skills with side effects get `disable-model-invocation: true` only when the user never asks for them in words: such a skill cannot be called through the Skill tool at all (the harness also forbids following it by other means). A skill the user asks for in words («закоммить») stays model-invocable and is limited by its description («only when the user explicitly asks») and by hooks
- `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` and `${CLAUDE_SKILL_DIR}` are substituted only in a skill or agent body loaded by Claude Code, not in files read with Read (`shared.md`, references)
- Hooks are bash + jq (node may come from nvm and be missing in the hook environment); test them by piping a JSON input into the script. Hooks run on every Bash call: check the raw input for a keyword (`[[ "$input" == *git* ]] || exit 0`) before the first `jq`
- Run `claude plugin validate .` before pushing; `.githooks/pre-push` runs `--strict` for the marketplace and every plugin (enable once: `git config core.hooksPath .githooks`)
- Evals live in `plugins/<plugin>/evals/`, run with `claude plugin eval plugins/<plugin>`
